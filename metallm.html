PART 01

Why domain models

A generalist knows a little about everything. Your domain needs an expert.

the generalist gapthe cost of fine-tuningfreeze & adapt

01.1 The problem with one big model

A generalist model is a jack of all trades

  • Generic answers — it doesn't know your domain's language, rules, or edge cases.
  • Full fine-tuning is expensive — GPUs, data pipelines, and a new checkpoint per domain.
  • It forgets — naive fine-tuning overwrites old skills to learn new ones.
  • And it leaks — sending domain data to a hosted model is a non-starter in regulated work.
One model can't be every expert

Freeze the base. Bolt on a tiny expert for each domain — and swap them like tools.

the MetaLLM idea

The base model already knows language and reasoning. MetaLLM keeps it frozen and trains small MicroLoRA adapters that carry only the domain — cheap to make, tiny to store, and composable at runtime.

  • Specialize — one adapter per domain, not one model per domain.
  • On-prem — training and inference stay inside the perimeter.
  • Composable — load the expert the task needs, drop it when done.
  • No forgetting — the frozen base and prior adapters are never overwritten.
The through-line

Same thesis as the rest of the stack — freeze the model, adapt around it. MetaLLM is that thesis applied to the weights themselves.

PART 03

How it specializes

Adapters, real-time adaptation, routing — and never forgetting what it knew.

MicroLoRASONAno forgettingrouting

03.1 MicroLoRA — the domain adapter

Freeze the base, train a tiny expert

  • Lightweight adapters — a few small weight matrices, not a new checkpoint.
  • Cheap to train — task-specific fine-tuning without touching the base.
  • Tiny to store & ship — a domain fits in a small, movable file.
  • Hot-swappable — load the health expert, then the security expert, on the same base.
Base frozen · adapter learned

03.2 SONA — real-time adaptation

It tunes itself while it works

  • Real-time neural adaptation — adjusts behaviour online, mid-task.
  • Under 0.05 ms — fast enough to sit on the hot path.
  • Learns from trajectories — successful patterns feed straight back in.
  • Pairs with MicroLoRA — adapters carry the domain, SONA carries the moment.
Trajectory → adaptation → better next call

03.3 Specialize without forgetting

New experts, and the old ones stay intact

  • The base is never overwritten — every domain is an additive adapter.
  • Adapters compose — stack or switch experts on one frozen core.
  • EWC++ in the stack — Elastic Weight Consolidation guards prior skills as new ones are learned.
  • No catastrophic forgetting — learning security doesn't erase health.
One base · a shelf of swappable experts

03.4 Routing & providers

Context routing

  • HNSW router — pulls the hot patterns relevant to the task.
  • ≤11 hot patterns — tuned for fast, small-corpus retrieval.
  • Larger corpora — hand off to AgentDB / RuVector embeddings.

One format, every provider

  • Claude · GPT · Gemini · Ollama · Cohere — chat-formatted identically.
  • Local or hosted — Ollama on-box, or a frontier API when you choose.
  • Swap providers without rewriting a prompt.
The point

The domain expert is stable; the runtime underneath it is interchangeable — same adapter, whichever model or provider is cheapest and most capable for the task.

03.5 Sovereign by construction

The whole loop can run inside your walls

  • Local inference on ruvLLM — the sovereign runtime the adapters ride on.
  • Train where the data lives — adapters are made on-prem; domain data never leaves.
  • Optional hosted — reach for a frontier provider only when you decide to.
  • Fits the edge — small adapters ship onto appliances, not a datacenter.
Adapters & inference stay on-prem

05.1 The workflow

Config, adapter, format — three skills

  • /ruvllm — shows model status, loaded adapters, and provider availability.
  • llm-config — generates an optimal local-inference config.
  • chat-format — formats a prompt for any supported provider.
  • Attach an adapter — pick the domain expert the task needs.
# check the model layer
/ruvllm status

# generate a local-inference config
skill llm-config --domain health

# format a prompt for a provider
skill chat-format --provider ollama

05.2 Drive it from the stack

One call for the agent, the whole layer underneath

  • Part of ruflo — MetaLLM is the model layer the harness calls into.
  • SONA + MicroLoRA pipeline is owned by the intelligence layer; the router by AgentDB.
  • Config namespace — adapters and manifests live under ruvllm-config.
  • Agent-ready — the domain expert is available to Claude Code / Codex as a tool.

06.1 Where MetaLLM fits

The specialist layer for a sovereign stack

Regulated verticals
Health, security, finance — a domain expert whose training data and inference both stay on-prem.
Edge appliances
Small signed adapters ship as cog modules onto a Cognitum Seed — an expert per box.
Agent stacks
ruflo agents call the right domain model per task, without prompt rewrites or new checkpoints.
Multi-provider shops
Keep the adapter, swap Ollama for a frontier API — one chat format across all of them.
The differentiator

Not a model zoo and not a hosted API — a freeze-and-adapt layer that makes domain experts cheap to build, tiny to ship, and sovereign to run.

06.2 Honest limits — stated plainly

What MetaLLM is, and isn't, today

  • A layer, not a monolith — capabilities are split across ruflo crates (intelligence owns SONA + MicroLoRA; AgentDB owns the router).
  • The HNSW router is small-corpus — capped at ≤11 hot patterns; larger retrieval belongs to AgentDB / RuVector.
  • Formats & quantization aren't publicly pinned — treat specifics as stack-dependent.
  • Part of an active stack — versions move; the honest framing moves with them.
The family voice

Same discipline as the rest of the ruv stack: claim what's measured, label what's early. MetaLLM is the domain-model layer — the specialist experts on top of a sovereign base.
