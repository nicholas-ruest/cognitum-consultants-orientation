PART 01

The big idea

Why the smartest move in agents right now is to stop chasing bigger models.

01.1 The problem

Every repo wants a repo-aware agent — and every agent burns money

Generic assistants don't know your codebase, your funnel, or your data. Tuning one by hand is slow; the obvious fix — a bigger model — is the expensive one.

  • Context gap — an off-the-shelf agent has no idea how your system actually works.
  • Cost gap — in a long-running app, LLM usage is your single biggest line item.
  • Trust gap — "it gets better over time" is usually an unfalsifiable claim.

Don't buy a bigger brain. Build a better harness around the one you have.

the MetaHarness thesis

The model's weights stay frozen. Everything around the model — how it plans, what context it sees, which tools it may call, when it retries — is the harness. That's what you evolve.

01.3 Why the harness is the cheapest lever

Cheapest capable model, best possible answer

The competitive advantage isn't only that it's smart — it's that it's the cheapest way to reach the best answer. Use a small model wherever it suffices, escalate to a frontier model only when a task truly demands it. That gap is your margin.

PART 03

Darwin — the engine

"Freeze the model, evolve the harness" — made mechanical.

03.1 @metaharness/darwin

Evolve the operating system around a frozen model

One policy surface mutates per generation. Each variant runs in a sandbox, gets scored, and is promoted only if it clears four hard gates — so improvement is measured, never assumed.

"Out of a hundred evolutions, this is the best one. The ones that work, it evolves more. The ones that don't are dead ends."

Reuven Cohen

03.2 The seven mutation surfaces

Exactly one changes per generation

planner.tsDecomposes a task into steps
context_builder.tsRanks file relevance
reviewer.tsRisk-file & test review
retry_policy.tsClassifies failures, retries
tool_policy.tsCommand allowlist & order
memory_policy.tsWhich outcomes to retain
score_policy.tsWeights — read-only to a variant
isolationOne change → one clean signal

Changing a single surface at a time keeps the causal signal clean — you know exactly which change moved the score.

03.3 The archive tree

Not a greedy climb — a population

Variants live in an archive tree, not a single best branch. Selection can revisit a weaker ancestor that turns out to seed a stronger lineage — exactly like biological evolution, where a dead end for one trait is the origin of another.

  • Keeps losers around — a low scorer may carry a mutation that pays off two generations later.
  • Opt-in strategies — quality-diversity, Pareto selection, crossover, MAP-Elites, curriculum learning.
  • Reproducible core — every extra is a toggle over a frozen, seeded baseline.

03.4 One generation, four steps

1
Mutate

Change exactly one surface → a child variant.

2
Sandbox

Run it shell-free, secrets scrubbed from the environment.

3
Score

Weighted sum of six 0–1 terms, minus penalties.

4
Promote

Replace the parent only if every gate holds; else it stays as an ancestor.

Everything lands in .metaharness/

  • archive.json — the population tree
  • lineage.json — graph for visualization
  • variants/ — one dir per variant
  • runs/ — traces & scores
  • reports/winner.json — the best result

03.5 The scoring model

Reward the outcome, punish the risk

A base score — the weighted sum of six 0–1 quality terms — minus a penalty layer that makes unsafe or wasteful behaviour uncompetitive by construction.

−0.30
secret exposure
−0.25
destructive actions
−0.20
hallucinated files
−0.15
tool loops

Also −0.10 for cost overrun. A variant literally can't win by cutting a dangerous corner.

03.6 The promotion gate

All four clauses must hold — or the child doesn't replace the parent

1

Score improves

Beats the parent by at least the delta.

2

Safety ≥ 0.95

On the independent safety check.

3

No regression

Test pass rate never drops.

4

Zero blocked

No blocked actions during the run.

This is what makes "it improved" a fact rather than a vibe — a promotion is a claim with four preconditions.

03.7 The safety model

Two independent checks, before code ever runs

Letting a system rewrite its own policies only works if it can't rewrite them into something dangerous. Darwin gates every variant twice, then runs it with no shell and no secrets.

  • inspectVariant() — disqualifies unapproved files, blocked names (.env, .git, secret), symlinks, and dangerous patterns (eval, fetch, child_process).
  • validateGeneratedCode() — gates any LLM-written code before it touches disk.
  • Shell-free sandbox — no command injection; scrubbed env exposes only PATH + identifiers, never secrets.

PART 04

Flywheel — the proof

Turning "self-improving" from a claim into a receipt.

04.1 @metaharness/flywheel

Perpetual motion — and a receipt for every gain

Darwin finds the cheapest, best model for a task. The Flywheel asks the best process — running continually, rewriting its own code, promoting only what proves measurable lift.

"Always looking, always evolving, always trying to make it better."

Reuven Cohen · on the flywheel

04.2 Four properties that make it trustworthy

immutable rule

Frozen gate

meetsPromotionRule can't drift mid-run to flatter a candidate.

compounding

Lineage

Each generation builds on the last promoted winner — season over season.

anti-Goodhart

Holdout + anchor

Must win on test sets it was never optimized against.

provenance

Ed25519 receipts

Signed promotions ship with a replay bundle.

Minimal by design — ESM, fully typed, runtime dependency is Node's native crypto and nothing else.

04.3 Anti-Goodhart construction

You can't game a metric you can't see

"When a measure becomes a target, it ceases to be a good measure." Flywheel defuses that: a candidate is optimized on one set but must prove itself on others it never touched.

  • Holdout set — unseen during optimization; catches overfitting.
  • Anchor set — a fixed reference that guards against silent regressions.
  • Clear both, or no promotion — a lucky run on the training slice isn't enough.

04.4 What you hand a skeptic

  • A lift curve — improvement you can see, not assert.
  • A promotion lineage — the chain of winners, and why each passed.
  • A replay bundle — reproduce the result on another machine.
  • Signed receipts — Ed25519 proof the run is the run.
// one verifiable improvement loop

05.3 Three ways to run it

Match the deployment to the client's appetite

simplest

Local

On your own machine — great for building, testing, and one-off evolutions.

scheduled

Claude schedule

A cloud version on a cron — hourly, daily. Cheaper, but no perpetual motion; it runs, then stops.

always-on

Your cloud + Flywheel

Cron is cheaper; perpetual motion compounds. The trade-off is cost vs. continuous improvement.
