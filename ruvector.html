PART 01

Why agents need memory

A model without memory starts every session from zero.

session amnesiathe substratelocal-first

01.1 The problem

Agents forget everything between sessions

  • No continuity — every run re-learns the same context.
  • Context windows aren't memory — they're a scratchpad that vanishes.
  • Bolting on a vector DB is heavy — servers, API keys, glue code.
  • Facts, episodes, skills all get thrown away at the end of a task.
Without a memory substrate

Freeze the model. Give it a memory that persists, adapts, and recalls.

the RuVector idea

RuVector is the substrate an agent writes to and reads from across sessions — facts, decisions, episodes, and skills — as vectors and a graph, on local disk, no external database required.

Remember · recall · adapt

01.3 Local-first by default

No servers, no API keys, no data leaving the box

  • Runs in-process — embeddings and search happen locally.
  • Local embeddings — all-MiniLM-L6-v2, cached on disk.
  • Hosted is optional — a Shared Brain augments, never required.
  • Portable — snapshots with compression & checksums for recovery.

PART 03

Four kinds of memory

Not one blob — the memory an agent needs, split by how it's used.

workingepisodicsemanticprocedural

03.1 The four memory types

One runtime — ruvllm — behind all four

now

Working

Current task context, scratchpad, tool cache — with TTL.

history

Episodic

Task trajectories: actions, observations, outcomes, critiques.

knowledge

Semantic

Facts with confidence, metadata, tagged collections, relationships.

how-to

Procedural

Skills, triggers, policies, and Q-values the agent reuses.

Why split it

Each type has a different shape, lifetime, and recall pattern. Splitting them lets RuVector store, decay, and retrieve each the right way — instead of one undifferentiated pile.

03.2 Working & episodic

Working — the here-and-now

  • Task context & scratchpad for the current run.
  • Tool cache with a time-to-live, so it expires cleanly.
  • Fast, ephemeral, not meant to last.

Episodic — what happened

  • Trajectories — the sequence of actions and observations.
  • Outcomes & critiques — what worked, what didn't, why.
  • Replayable — the raw material for learning later.
The bridge

Episodic memory is meant to consolidate into semantic facts and procedural skills over time — the way experience becomes knowledge.

03.3 Semantic & procedural

Semantic — what's true

  • Facts with confidence scores — not everything is certain.
  • Metadata & tags — filterable, organized into collections.
  • Relationships — linked in the graph, not isolated rows.

Procedural — how to act

  • Skills & triggers — reusable know-how, invoked on cue.
  • Policies & Q-values — learned preferences over actions.
  • Outcome-aware — routing adjusts as results come in.
Security note

Embeddings are treated as sensitive derivatives of their source — same classification. Collections organize memory; they are not an authorization boundary.

04.1 The memory lifecycle

Five stages, one substrate

encodeCapture

Embed text into vectors, locally.

storePersist

Index in HNSW + graph, LSM writes.

retrieveRecall

Dense+sparse fusion, decay, rerank.

tuneLearn

MicroLoRA + EWC++ adapt recall.

shrinkConsolidate

Compress, quantize, condense.

The whole loop is local

Everything from embedding to reranking runs in-process — the network is optional, not on the critical path.

04.2 Capture & encode

Text in, vectors out — no API call

  • Local ONNX embeddings — all-MiniLM-L6-v2, cached on disk.
  • Batch & parallel encoding for throughput.
  • Provenance tracked — model, dimension, normalization.
  • External providers supported when you want them.
Embed once, search forever

04.3 Persist & organize

Indexed for search, linked for meaning

  • HNSW or flat index — pick latency vs. exactness.
  • Graph & hypergraph store explicit relationships.
  • High-write LSM architecture for fast ingestion.
  • Namespaces & aliases — isolation and clean rollover.
HNSW · greedy descent through layers

04.4 Recall & reconstruct

Better recall than raw nearest-neighbour

  • Sparse + dense fusion — keywords and meaning together.
  • Temporal decay — recency without losing the important old.
  • Coherence gating — trust memories the graph supports.
  • MaxSim + GNN rerank — late interaction, learned ordering.
Two signals fused into one ranking

04.5 Temporal coherence

Recent memories weigh more — gently

  • Temporal decay down-weights stale memories over time.
  • Coherence keeps old memories the graph still supports.
  • Tunable — control how fast the past fades.

A proof-of-concept today (exact graphs); production uses approximate neighbours.

Recall weight vs. age

04.6 Learn & adapt

Recall that improves without forgetting

  • SONA MicroLoRA — tiny adapter weights, cheap to train.
  • EWC++ — Elastic Weight Consolidation stops catastrophic forgetting.
  • Outcome-aware routing — results feed back into ranking.
  • Self-reconstructing graph memory repairs its own links.
Frozen base + small learned adapter

04.7 Consolidate & compress

Keep more memory in less space

  • Product quantization — compressed vectors, fast search.
  • RaBitQ — one-bit candidate encoding for cheap first-pass.
  • Matryoshka — coarse-to-fine embeddings, truncate on demand.
  • Graph condensation — shrink links, keep provenance.

Using RuVector

A CLI, a Node API, and MCP — pick your surface.

05.1 The CLI — npx ruvector

Give any agent memory with hooks

  • remember / recall — write and read memories by type.
  • reembed — re-encode after a model change.
  • stats / verify — inspect and check integrity.
  • mcp start — expose memory as MCP tools.
# remember a decision
npx ruvector hooks remember --semantic \
  --type decision "use HNSW for recall"

# recall the top matches
npx ruvector hooks recall --semantic \
  --top-k 3 "which index did we pick?"

npx ruvector mcp start   # serve as MCP

RuVector — on measuring honestly

Benchmarks ship as reproducible code, not marketing numbers.

  • Core search — cargo bench -p ruvector-core.
  • High-write — the lsm-ann benchmark binary.
  • Temporal, cap-gated, Matryoshka — each with its own bench.
  • Always paired — latency reported against a recall target.

Known limits (stated plainly)

  • Modular monorepo — one install doesn't light up every crate.
  • Consolidation WIP — episodic→semantic isn't fully wired.
  • Cold start rebuilds the HNSW index by enumeration.
  • Research surfaces — GNN rerank, cap-gated ANN, Raft are not automatic.
